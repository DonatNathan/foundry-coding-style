# Workshop Coding Style

> Keep your modules nice and clean.

_Last checked against Workshop and its documentation on 2026-11-24._

This document gathers the rules, guidelines and conventions that Foundry builders and Forward Deployed Engineers follow when building **Workshop** applications. It merges two sources:

- **Official**: best practices published in the [Palantir Foundry documentation](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices). Each official rule links to its source.
- **House**: rules that are not in the documentation but that we enforce. Each house rule gives its reason.

It applies to:

- naming (variables, widgets, sections, pages, folders),
- variable organization,
- module structure and embedded modules,
- layout,
- components (tables, buttons, filters),
- events,
- performance.

> [!IMPORTANT]
> The coding style is a convention, not a substitute for a working application. A module that follows every rule and does not do what its users need is still a bad module.

It is easier and quicker to follow this style from the start of a module than to clean up an existing module at the end.

When you face a choice that this document does not cover, pick the option that makes the module **clearer for the next builder** and **simpler for the end user**.

## Rule Codes

Severity levels, rule sources, exceptions and implicit rules are shared by every guide: see [How to Read the Guides](README.md#how-to-read-the-guides).

Workshop rules use the `W-` prefix followed by a category letter and a number:

```
W-<Category><Number>        e.g. W-N3, W-M1, W-L1
```

| Prefix | Category |
|---|---|
| `W-N` | Naming |
| `W-V` | Variables |
| `W-M` | Modules and structure |

| `W-C` | Components |
| `W-E` | Events |

## N — Naming

> [!NOTE]
> **Why plain language instead of `camelCase` or `snake_case`?**
> Workshop is not a code editor. Its variable search matches individual words, names are compared case-insensitively (`MyVar` and `myvar` are duplicates), and non-developers read these names.
>
> The [variables documentation](https://www.palantir.com/docs/foundry/workshop/concepts-variables) shows examples such as `$page_Dashboard_filterState`. **We deliberately do not follow that example.**

### W-N1 — Language and Casing

🔴 **Major** · House

All names (variables, widgets, sections, pages, folders, modules) are written **in English**, in **Title Case**, with words separated by **spaces**.

- Capitalize every word except articles, short conjunctions and short prepositions (`a`, `an`, `the`, `and`, `or`, `of`, `by`, `in`, `on`, `for`, `to`, `per`), unless they are the first word.
- Acronyms stay uppercase (`KPI`, `ID`, `SLA`).

```
✅ Selected Order
✅ Count of Open Orders
✅ Orders Filtered by Status
✅ KPI Revenue per Region

❌ selectedOrder            (camelCase)
❌ selected_order           (snake_case)
❌ $page_Orders_selected    (code-style prefix)
❌ selected order           (not Title Case)
❌ Commande Sélectionnée    (not English)
```

### W-N2 — Descriptive Names

🔴 **Major** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

A name must describe **what the element holds or shows**, clearly and unambiguously. Default names generated by Workshop are forbidden in a shared module.

```
✅ Late Shipments
✅ Shipment Details Panel

❌ Object Set 3
❌ String Variable 1
❌ Data
❌ Temp
```

Abbreviations are tolerated only when they are widely known to the readers (`KPI`, `ID`, `SLA`). Do not invent abbreviations (`Shpmt Cnt`).

### W-N3 — Prefixes

🟡 **Minor** · House

A prefix gives the **scope** of a variable, never its type.

**Scope prefix.** When a variable serves **only one part** of the module, prefix it with that part's name in brackets. A scope can be a page, a section, a form, an Action or an overlay.

- The scope follows W-N1 and matches the name of the element it refers to, without the element kind (section `Order Details Panel` → `[Order Details]`).
- Use **one** prefix only. Do not chain scopes (`[Orders Page] [Filters]`).
- A variable used by **several** scopes has **no** prefix.

**Forbidden prefixes.**

- No **type** prefixes (`[s]`, `[bool]`, `[os]`) or type suffixes. The Variables panel can filter by type, and the icon already shows it.
- No **module interface** prefixes (`[Input]`, `[Output]`). The Variables panel can filter on the module interface.
- No `[Global]` prefix. Shared variables have no prefix.

```
✅ [Order Form] Comment Input
✅ [Approve Order] Rejection Reason
✅ [Filters] Selected Statuses
✅ [Order Details] Is Edit Mode On
✅ Selected Order                      (used by several sections: no prefix)

❌ [s] Order Comment Input             (type prefix)
❌ Order Comment Input String          (type suffix)
❌ [Input] Selected Site               (use the module interface filter)
❌ [Global] Current User Region        (shared variables have no prefix)
❌ [Orders Page] [Filters] Statuses    (one prefix only)
❌ [Order Details Panel] Due Date      (drop the element kind)
```

> [!TIP]
> Folders do not appear when you pick a variable from a widget's input dropdown. Only the name does. That is why the scope lives in the name.

### W-N4 — Naming by Role

🟡 **Minor** · House

Most variables play one of a few recurring roles. Name them with the matching pattern so any builder can guess a variable's purpose from its name.

| Role | Pattern | Example |
|---|---|---|
| Base object set | `All <Objects>` | `All Orders` |
| Filtered object set | `<Objects> Filtered by <Criteria>` or `<Adjective> <Objects>` | `Orders Filtered by Status`, `Late Orders` |
| Filter output | `<Objects> Filter` | `Orders Filter` |
| Selection (single) | `Selected <Object>` | `Selected Order` |
| Selection (multiple) | `Selected <Objects>` | `Selected Orders` |
| Aggregation | `<Metric> of <Objects>` | `Count of Late Orders`, `Sum of Order Value` |
| Object property | `<Object> <Property>` | `Selected Order Due Date` |
| User input | `<Subject> Input` | `Order Comment Input` |
| Constant | `<Subject> <Unit>` | `Late Threshold Days` |
| Function output | `<Result>` (what it returns, not the function name) | `Forecast Revenue` |

### W-N5 — Boolean Names

🟡 **Minor** · House

A Boolean variable is named as a **yes/no question**, starting with `Is`, `Has`, `Can` or `Show`.

```
✅ Is Details Panel Open
✅ Has Edit Rights
✅ Show Archived Orders

❌ Details Panel
❌ Edit
❌ Toggle 2
```

### W-N6 — Ontology Vocabulary

🟡 **Minor** · House

When a name refers to an object type or property, use **its display name in the Ontology**, singular or plural as needed. Do not use synonyms.

```
Ontology object type: "Purchase Order"

✅ Selected Purchase Order

❌ Selected PO
❌ Selected Order
```

### W-N7 — Widget and Section Names

🟡 **Minor** · House

Name widgets and sections after their **content**, followed by the **kind of element**. The icon already shows the widget type, so the name must add the content.

```
✅ Late Orders Table
✅ Order Details Panel
✅ Revenue KPI Card
✅ Filters Section

❌ Object Table 3
❌ Table
❌ Section 12
```

### W-N8 — Pages, Overlays and Folders

🔵 **Info** · House

Page, overlay and folder names follow W-N1 and describe a **user goal or feature**, not a technical grouping (`Misc`, `Stuff`, `New`).

Like widgets and sections (W-N7), pages and overlays end with their **element kind**:

- Pages: `<Goal> Page`
- Overlays: `<Purpose> Overlay`
- Folders: no suffix, since they only contain variables.

```
✅ Dashboard Page
✅ Order Review Page
✅ Creation Form Overlay
✅ Delete Confirmation Overlay

❌ Dashboard                 (missing element kind)
❌ Page 2
❌ Overlay 1
❌ Misc Page
```

When used as a scope prefix (W-N3), drop the element kind: `Creation Form Overlay` → `[Creation Form]`.

## V — Variables

### W-V1 — Variable Folders

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

Group related variables in **variable folders** that mirror the scope prefixes of W-N3.

Folders are a complement to prefixes, not a replacement. They do not appear in widget input dropdowns, and the feature is still limited today. This rule may become 🟡 Minor once folders improve.

```
✅ Order Form/
     [Order Form] Comment Input
     [Order Form] Delivery Date Input
   Approve Order/
     [Approve Order] Rejection Reason
```

### W-V2 — No Orphan Variables

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

A variable used by no widget, event or downstream variable must be deleted. Use the variable lineage graph to check. Orphan variables are dead code.

### W-V3 — One Job per Function-Backed Variable

🟡 **Minor** · House, supported by [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

A function-backed variable computes **one thing**. Do not write one large Function that returns every KPI of a page.

Why:

- Workshop loads variables lazily. One large Function computes everything even when the user only sees one value.
- The computation-time view and the lineage graph cannot tell you which part is slow.
- The official documentation recommends splitting slow function-backed variables into smaller pieces.

```
✅ Count of Late Orders        (aggregation variable)
✅ Average Delay Days          (function: getAverageDelayDays)

❌ All Page KPIs               (function returning a struct with 12 values)
```

### W-V4 — Prefer Native Definitions

🔵 **Info** · House

When a native variable definition does the job (object set filter, object set aggregation, object property), use it instead of a Function. Native definitions are visible in the lineage graph, need no code review, and do not need a repository to be maintained.

Use a Function when the logic cannot be expressed natively or would require a long chain of variables.

### W-V5 — Limit Shared Variables

🔵 **Info** · House

Keep variables shared by several scopes (variables without a prefix, see W-N3) to the minimum. Every shared variable is a hidden dependency between parts of the module. When a variable is only used in one place, scope it.

### W-V6 — Named Constants

🔵 **Info** · House

A non-trivial value used in several places (a threshold, a default date range, a status list) is stored in a **static variable with a name**, not typed again in each widget or filter.

```
✅ Late Threshold Days = 7        (used by 3 filters)
❌ "7" typed directly in 3 filters
```

## M — Modules and Structure

### W-M1 — Maximum 50 Variables per Module

🔴 **Major** · House

A module, or an embedded module, must not contain **more than 50 variables**. Beyond that, split the module into embedded modules, each representing a logical entity (see W-M2).

Why: a Palantir Workshop team member notes that modules with hundreds of variables become unwieldy ([community thread](https://community.palantir.com/t/workshop-variables/6743)), and the documentation recommends embedded modules to "reduce the number of variables" ([FAQ](https://www.palantir.com/docs/foundry/workshop/application-design-faqs)). 50 is our threshold: past it, a builder can no longer see the whole module in one scroll of the Variables panel.

> [!TIP]
> Past 30 variables, start planning the split. Splitting at 50 is easier than at 150.

### W-M2 — Module Coherence

🔴 **Major** · House

A module (or embedded module) represents **one logical entity**: one user flow, one object view, or one feature. If you cannot describe what the module does in one sentence without "and", split it.

```
✅ Order Review            (review and validate one order)
✅ Supplier Overview       (KPIs and list of one supplier's orders)

❌ Orders and Suppliers and Admin
```

### W-M3 — Embedded Modules for Reuse

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-faqs)

When the same interface appears on several pages or in several applications, build it **once** as an embedded module. Do not copy and paste sections between modules.

### W-M4 — Module Interface

🟡 **Minor** · House

The interface variables of an embedded module are its public API, like a function's arguments.

- Name them like any other variable (W-N1, W-N4), without an `[Input]` or `[Output]` prefix. Use the module interface filter of the Variables panel to find them.
- An embedded module should not need **more than 6 interface variables**. If it needs more, it probably does more than one thing (W-M2).

### W-M5 — Embedding Depth

🟡 **Minor** · House

Do not nest embedded modules **more than 3 levels deep** (parent → child → grandchild). Deeper nesting makes the data flow hard to follow and to debug.

### W-M6 — Design Before Building

🔵 **Info** · Palantir ([community thread](https://community.palantir.com/t/workshop-variables/6743))

Sketch the pages, the embedded modules and their interfaces **before** building. Splitting a large module afterwards is much more expensive than planning it.

## L — Layout

### W-L1 — Maximum 10 Components per View

🔴 **Major** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

A single view must not display **more than 10 visible components** (buttons, panels, widgets). Limit the number of actionable items (tasks, notifications, choices) per screen.

### W-L2 — Maximum 5 Primary Navigation Actions

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Top-level navigation must not have **more than 5 primary actions**.

### W-L3 — Whitespace

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Aim for **30 to 40% whitespace** on each screen. If the screen looks crowded when you squint at it, it is.

### W-L4 — Header Hierarchy

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Use exactly three levels of headings:

1. **Page header**: largest text, sets the page's purpose.
2. **Section header**: groups related content.
3. **Description** (subheading of a section header): short, only when needed.

### W-L5 — Spacing and Elevation

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

- Use **Compact** padding by default. For custom padding, use 80% height or width and 16px spacing.
- Use containers to separate different content groups, and dividers to separate related content within a section.
- Apply **shaded padding at most once per page**.
- Reserve the **outer drop shadow** for the main content or the primary modal.
- Lighter backgrounds mark important content. Darker backgrounds mark secondary content (filters, collapsible panels).

### W-L6 — Filters on the Left

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Anchor filter widgets in the **left-most** section of the page. Content flows left to right and top to bottom (F-shaped reading).

### W-L7 — No Horizontal Scrolling

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Avoid horizontal scrolling. On Object Tables, enable **Fit columns horizontally**. Keep navigation bars and tabs in the primary header so only content sections scroll.

### W-L8 — Touch Targets

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

When scrolling is enabled, every touch target (buttons, etc.) is **at least 30px**.

### W-L9 — No Stacked Collapsible Sections

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-faqs)

Do not stack collapsible sections. Use a hidden section opened by a button when a collapsible section is already in place.

### W-L10 — Overlays

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

- Use overlays only for **temporary or secondary** interactions (forms, questionnaires).
- Do not use overlays for **analytical** content that users need to compare with the page.
- Use a **centered pop-up** for critical tasks that need full attention (confirmations, alerts, action forms).
- Use a **drawer** for secondary tasks that should keep the main content visible.

### W-L11 — Typography

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Keep the default font or use a **system font**. A custom font only renders if it is installed on the viewer's device.

### W-L12 — Consistent Look Across Modules

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-best-practices)

Modules of the same application share the same header layout (logo top-left, global settings top-right) and the same styles for tabs, Metric Cards, headers and buttons.

## C — Components

### W-C1 — Tables Show Counts

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

Every Object Table, Object List and Pivot Table shows its row count, using a Metric Card with the **Tag** layout in the section header.

### W-C2 — Button Intents

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

| Intent | Color | Use for | Examples |
|---|---|---|---|
| None | Gray | Secondary actions | Back, Skip, Cancel |
| Primary | Blue | Main call to action | Create, Add New, Next |
| Success | Green | Completion or positive outcome | Submit, Save, Approve |
| Warning | Amber | Needs attention, not destructive | Archive, Suspend |
| Danger | Red | Destructive or hard to undo | Delete, Remove |

### W-C3 — Destructive Actions Use Danger

🔴 **Major** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

A button that deletes data or triggers an action that cannot easily be undone **must** use the **Danger** intent, and no other button may use it.

### W-C4 — One Primary Action per Group

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

- Each button group has **one** primary action, placed **first** (left).
- Order the remaining buttons left to right by importance. Move rarely used actions into a menu.
- Do not give every button its own color.
- Place buttons next to the section or widget they act on.

### W-C5 — Button Labels

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

- Button labels are **user-facing text**, not names. They follow the official guidance: **sentence case**, natural language, starting with a verb (`Approve order`, `Add comment`).
- Add an icon that shows the action. Horizontal arrow: navigation inside the module. Angled arrow: opens a new tab. `+`: related actions. Ellipsis: menu of independent actions.
- Do not repeat what the section header already says.

> [!NOTE]
> Title Case (W-N1) applies to **names** that builders see. Sentence case applies to **labels** that end users read on buttons.

### W-C6 — Choosing a Filter Widget

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-components)

| Need | Widget |
|---|---|
| Several filters at once, complex cases | Filter List, **Vertical** layout |
| Few filters, limited space, beginner users | Filter List, **Pills** layout, or Exploration Filter Pills |
| Keyword, property or complex queries for experienced users | Exploration Search Bar |

### W-C7 — Object Table or Object List

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/application-design-faqs)

Use an **Object Table** to compare several properties, sort, or run bulk actions. Use an **Object List** for simple content with few properties and single-item actions. Show extra details in a **collapsible detail panel** rather than an overlay.

## E — Events

### W-E1 — Events Do Not Wait for Recomputation

🔴 **Major** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-events)

Events run in their configured order, but they **do not wait** for downstream variables to recompute. If an event depends on a value that a previous event changes, split the flow into separate user-triggered steps.

### W-E2 — Short Event Chains

🟡 **Minor** · House

A single trigger should not chain **more than 5 events**. A longer chain is hard to debug and usually hides logic that belongs in an Action or a Function.

## P — Performance

### W-P1 — Use Lazy Loading

🟡 **Minor** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

Workshop only computes a variable when it is needed. Put heavy content in tabs or hidden sections so it does not compute on page load.

Be aware that variables used by **layout visibility** settings are still computed while hidden.

### W-P2 — Check Computation Time Before Release

🔵 **Info** · [Official](https://www.palantir.com/docs/foundry/workshop/concepts-variables)

Before sharing a module, open the **variable lineage graph** with **computation time** enabled. Slow variables are candidates for splitting (W-V3) or for a different recompute setting.
